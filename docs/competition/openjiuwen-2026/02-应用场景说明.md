# 应用场景说明

## 所属主题 / 方向

| 优先级 | 方向 | 对应本作品能力 |
|--------|------|----------------|
| 主赛道 | **Coding** | 代码审查、Bug/CI 归因、补丁建议、Git/PR 生产力 |
| 兼报 | **科研** | 社区 Issue/PR/师生审核对话采集与模式沉淀，支撑复现研究 |

（FAQ 允许一队选多个方向，但仍只提交 **1 个作品**。）

## 目标用户

1. **昇腾社区贡献者 / 学生**：做算子社区任务、API 一致性、torch-npu PR，需要按任务书与官方 skill 自检。
2. **AI Infra 工程师**：迁移模型到 NPU、排查 HCCL/ACL/CI 失败，需要可引用的案例与文档。
3. **社区导师 / 审核人**：希望 Agent 先归纳讨论与门禁结论，减少重复口头反馈。
4. **openGauss 等兄弟社区贡献者**：复用同一套「取证 → 专业路由 → 报告」范式。

## 需求痛点

| 痛点 | 现状 | Agent 如何解 |
|------|------|--------------|
| 规则散落 | design 模板、精度标准、赛事说明分多仓 | 场景路由 + Skills 按预算加载，规则可溯源 |
| 助手只聊天 | 通用模型不懂 GitCode / 社区口径 | URL 取证、本地案例检索、昇腾 MCP 文档 |
| 改代码不安全 | 模型直接改仓、乱 force | 补丁预览确认链；Git 安全护栏 |
| 知识难沉淀 | 审核对话与 CI 流失 | `collect` 采集 issues/PRs/CI/师生对话 |
| 多社区切换 | 昇腾与 openGauss 规则不同 | 第三场景 `opengauss` + 专用 advisor |

## 典型使用故事（3 个）

### 故事 A：社区任务自检（Coding）

贡献者认领 AscendC 任务后运行 `reviewagent`，粘贴 design PR 链接。Agent 识别算子场景，加载 `cann-op-checker` 与 `cann-ascendc-op-dev`，对照红线输出 BLOCKER/WARN，并给出补测建议。

### 故事 B：CI 红了不知道看哪（Coding）

开发者粘贴失败日志或 `/ci`，启发式归类 ACL/HCCL/codecheck；必要时 MCP 查昇腾文档；确认后 `/fix` 生成补丁，`/ship` 逐步提交开 PR。

### 故事 C：导师复盘审核话术（科研 / 社区）

`reviewagent collect --community opengauss`（需 `GITCODE_TOKEN`）拉取 Plugin/docs 的讨论与 CI，对话按 author/reviewer 角色标注，供后续 skill 与报告引用——服务「老师—学员」社区辅导场景。

## 场景价值

- **个人**：缩短「查文档 + 对任务书 + 看 CI」闭环。
- **社区**：统一审查口径，降低导师重复劳动。
- **企业**：可离线规则兜底 + 自备模型网关（DeepSeek / OpenAI 兼容 / Claude / GLM），适配内网。

## 边界（诚实表述）

- 不替代真实 NPU 上板验证；精度/性能数字以任务书与实测为准。
- 不自动执行破坏性 MCP 工具；自定义 MCP 源需用户自担风险。
- 初赛阶段未强制绑定 openJiuwen WorkSwarm；DEMO 阶段可演进为平台工具/工作流节点。
